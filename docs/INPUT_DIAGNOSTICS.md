# Controller input diagnostics (`RTCWInput`)

Added in M2A. A lightweight, rate-limited trace of the controller input path, meant to be collected from a
real headset (for example by the Windows Feedback Bridge) after a short test.

- Source: `Projects/Android/jni/RTCWVR/VrInputDiag.c` / `.h`
- Logcat tag: **`RTCWInput`**, priority Info
- Collect: `adb logcat -s RTCWInput:I` (or add `RTCW:I` to also get the engine's own `VR controllers found: ...` line)
- Control: console cvar `vr_input_diag` — `1` (default) = state changes only, `0` = silent. It is not archived,
  so every launch starts at `1`.
- Volume: events are logged on **state change only**, never per frame. A token bucket (burst 40, 20 lines/s) is a
  safety net; if it ever trips, an `ev=drop n=<count>` line reports how many lines were lost. One `hb`
  heartbeat line every 5 s shows the loop is alive.

## Line format (version `v1`)

```
v1 t=<ms> ev=<name> <key>=<value> <key>=<value> ...
```

- One event per line, fields separated by single spaces, values never contain spaces.
- `t` is the engine millisecond clock (`Sys_Milliseconds`).
- Reference regex: `^v1 t=(\d+) ev=(\w+)(?: (.*))?$`, then split the remainder on spaces and on the first `=`.
- Hands are `L`, `R`, or `?` (a key generated by a state that is neither hand).
- Unknown future fields must be ignored by parsers; the `v1` prefix changes only on a breaking format change.

## Events

| `ev` | Fields | Emitted when |
|---|---|---|
| `ext` | `name`, `enabled` | Instance creation: whether the optional OpenXR extension `XR_BD_controller_interaction` was advertised and enabled. |
| `suggest` | `profile`, `result`, `name`, `bindings`, `retry` | Once per interaction profile (and once more with `retry=1` if the full PICO set was rejected). `result=0` means the runtime accepted the bindings. |
| `attach` | `result`, `name` | `xrAttachSessionActionSets` finished. |
| `sync` | `result`, `name` | `xrSyncActions` result, first time and whenever it changes. `XR_SESSION_NOT_FOCUSED` (8) means all actions are inactive. |
| `profile` | `hand`, `path` | The interaction profile the runtime bound to a hand changed (polled about 3 times per second). `path=none` after a profile existed. |
| `actionerr` | `hand`, `action`, `result`, `name` | `xrGetActionState*` failed (deduplicated). |
| `active` | `hand`, `mask`, `actions` | First sample, and whenever the set of **active** actions changes. `mask` bit order: 0 trigger, 1 grip, 2 face1 (X/A), 3 face2 (Y/B), 4 menu, 5 stickclick, 6 select, 7 stick. |
| `btn` | `hand`, `name`, `down`, `val`, `active`, `buttons` | A button crossed its pressed state. `name` is `trigger`, `grip`, `X`/`Y` (left), `A`/`B` (right), `menu`, `stickclick`, `select`. `val` is the raw action value, `buttons` the composed `Buttons` bitmask (hex) after the change. Analog actions use the 0.5 threshold. |
| `trigpeak` | `hand`, `max`, `note` | A trigger pull moved but never crossed 0.5 before release (a scaling or binding problem). |
| `menuhand` | `cursor`, `menu_right_handed`, `controls_left`, `screen` | Which physical hand drives the menu cursor and clicks changed. |
| `key` (`stage=gen`) | `hand`, `name`, `code`, `down` | A controller button queued an engine key event (`Sys_QueEvent`). `name` is `MOUSE1`, `ESCAPE`, `SPACE` or `other`. |
| `key` (`stage=deliver`) | `name`, `code`, `down`, `catchers`, `route` | The engine dispatched the event in `CL_KeyEvent`. Only `MOUSE1`, `ESCAPE`, `SPACE` are reported. `route` is `ui`, `console`, `cgame` or `game` from `cls.keyCatchers`. |
| `hb` | `frames`, `profileL`, `profileR`, `sync`, `mouse1_gen`, `mouse1_deliver`, `dropped_total` | Every 5 s. `frames` = input updates since the last heartbeat; the counters count MOUSE1 presses. |
| `drop` | `n` | The rate limiter discarded `n` lines. |

## Reading a trace: where does the chain stop?

The menu click path is: runtime profile -> bindings accepted -> action active -> `btn` change -> `key stage=gen` ->
`key stage=deliver route=ui` -> menu activates. Find the first missing link:

1. `ev=ext ... enabled=0` on a PICO 4: the runtime does not advertise `XR_BD_controller_interaction`; the PICO 4
   profile cannot be used, expect a fallback profile.
2. `ev=suggest profile=bytedance/pico4_controller result=<non-zero>`: bindings rejected (`XR_ERROR_PATH_UNSUPPORTED`
   = -22 or similar). Check whether `retry=1` succeeded.
3. `ev=profile hand=R path=...`: which profile the runtime really used. `khr/simple_controller` has only a select
   click, mapped to the trigger since M2A. `none` means no controller profile was bound.
4. `ev=active hand=R mask=...` without the trigger bit (`0x01`): the trigger action is not bound or not active.
5. `ev=sync result=8 name=XR_SESSION_NOT_FOCUSED`: the app was not focused, so no input was delivered.
6. Trigger pulls with `ev=trigpeak` but no `ev=btn name=trigger`: values never reach 0.5.
7. `ev=btn name=trigger down=1` present but no `ev=key stage=gen name=MOUSE1`: the menu hand logic is routing the
   click to the other hand; compare `ev=menuhand cursor=...` with the hand on the `btn` line.
8. `stage=gen` present but no `stage=deliver`: events are lost between `Sys_QueEvent` and `CL_KeyEvent`.
9. `stage=deliver route=ui` present but nothing activates: the problem is inside the UI (cursor focus), not input.

## Related (M2B)

Cinematic (`RTCWCinematic`) and pointer (`RTCWPointer`) diagnostics use the same line format and are documented in
`docs/M2B_CINEMATIC_POINTER_DIAGNOSTICS.md`. M2B adds one `RTCWInput` event:

| `ev` | Fields | Emitted when |
|---|---|---|
| `release` | `reason` (`to_screen`/`to_game`), `actions`, `keys` | The screen-layer mode changed while the VR layer still held `+actions`/keys it started; they were released. |

## Notes

- The pre-existing engine line `VR controllers found: <profile path>` (tag `RTCW`) is printed once when the right
  hand profile is first known; it already answers step 3 for older builds.
- Diagnostics add no engine state and do not change input behaviour; they only observe it.
